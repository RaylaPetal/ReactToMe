## Context

See proposal.md - Why. Today `ReactionTrigger` implicitly assumes emote-only matching (`TriggerMatcher.FindMatch` checks `EmoteId`/`Scope` directly), `EmotePoller` detects emotes by polling `Character.EmoteController.EmoteId` off every nearby `IPlayerCharacter`'s struct each frame and diffing against a last-seen value per actor, and `ConfigWindow.Draw()` renders every trigger as a `CollapsingHeader` with every field stacked vertically inside it. `IChatGui` is only ever used today to *send* messages (`ChatMessageSender`) or print warnings — nothing subscribes to incoming chat.

FFXIVClientStructs' `Character` exposes `GetCastInfo()` returning a `CastInfo*` with `ActionId` and an `IsCasting` bit, populated for any nearby character with an active cast (confirmed against aers/FFXIVClientStructs source) — the same "read a public struct field off any nearby Character" shape `EmotePoller` already uses, extendable to job-skill detection for both self and others with no hook. This only covers actions with a cast time; instant actions never populate `CastInfo` and are out of scope here.

## Goals / Non-Goals

**Goals:**
- Generalize trigger *sources* (emote / chat phrase / job skill) and trigger *reactions* (existing four + gesture) without a disruptive rewrite of the underlying config storage.
- Reorganize the config screen so it scales with more fields, reusing the existing window rather than adding another one.
- Make a previously-silent Penumbra IPC failure visible.

**Non-Goals:**
- Instant (non-cast-time) action detection — needs a heavier network-effect hook, a separate future investigation.
- Configurable chat channel sets — v1 watches a fixed list.
- A polymorphic/tagged trigger data model (e.g. separate source subclasses) — out of scope; see Decision 1.
- Retry or timing-workaround logic for the Penumbra bug beyond surfacing the failure — see Decision 6.

## Decisions

### Trigger data model
1. **Keep `ReactionTrigger` a single flat class with a `TriggerSourceType` discriminator**, rather than introducing per-source-type subclasses or a polymorphic hierarchy. New fields (`ChatPhrase`, `ChatTriggerSource`, `JobSkillActionId`, `GestureEmoteId`, `Name`) are added alongside the existing ones; `TriggerMatcher` and the UI both branch on `TriggerSourceType` to decide which fields matter. This matches the existing convention where "unset" sentinel values (`Guid.Empty`, `0`, empty string) already mean "not configured" — adding a discriminator to select among several optional groups of fields is a small, consistent extension, not a new pattern. A polymorphic model would be more type-safe (can't accidentally read a chat-phrase field on an emote-sourced trigger) but requires reworking JSON (de)serialization of the trigger list and every consumer; not worth it for three source types.
2. **`TriggerMatcher.FindMatch` gains a `TriggerSourceType` switch** with one matching path per type; the emote path is the existing logic unchanged. Chat-phrase and job-skill matching become new sibling methods called from the same switch.

### Chat-phrase triggers
3. **A new `ChatMessageListener` subscribes to `IChatGui.ChatMessage`**, filtering to the fixed channel set (Say/Yell/Shout/Tell/Party/Alliance/FreeCompany) and exposing an event carrying the message text and whether the sender was the local player — mirroring `EmotePoller`'s event-based shape (`EmotePerformedEventArgs`) so `Plugin.cs` wires both the same way.
4. **Matching is case-insensitive substring**, not exact-match or regex — simplest option satisfying "spank react" appearing anywhere in a real chat line (which often carries a sender name prefix or trailing punctuation depending on channel formatting). No per-trigger regex support in v1.
5. **`ChatTriggerSource` (`SelfTyped` / `AnyoneNearby`) is a new, separate enum from `TriggerScope`**, not a reuse of it — `TriggerScope`'s "OthersTargetingMe" encodes a real in-game *target*, which chat messages don't have. Reusing it would leave a nonsensical option (targeting) exposed for a source type where it can't apply.

### Job-skill triggers
6. **A new `JobSkillPoller` mirrors `EmotePoller` exactly**: same per-frame loop over `IObjectTable`, same per-actor last-seen-value cache, reading `Character.GetCastInfo()->ActionId` and `IsCasting` instead of `EmoteController.EmoteId`, firing an event on a `false -> true` transition of `IsCasting` (start-of-cast, not every frame while still casting). Reuses `TriggerScope` as-is, since a cast has a real target (`CastInfo.TargetId`) the same way an emote does.
7. **The action catalog groups by job, not one flat action list.** The unfiltered Lumina Action sheet is thousands of rows including NPC/monster-only actions, PvP variants, and role/general actions with no single owning job — a flat picker over all of it was unusably noisy (duplicates and irrelevant entries). The catalog instead filters to `IsPlayerAction && !IsPvP && ClassJob.RowId != 0` (confirmed against Lumina.Excel.dll's actual `Action`/`ClassJob` sheet fields), groups the result by owning `ClassJob`, and exposes a job list plus a per-job action list. The config UI picks a job first, then a skill from that job's own list — `ReactionTrigger` gained a `JobSkillClassJobId` field to remember which job is selected (UI convenience only; matching still keys purely on `JobSkillActionId`).

### Gesture reaction
8. **`EmoteCatalog` is extended to also resolve each emote's slash command text** (Lumina's `Emote` sheet is expected to reference a `TextCommand` sheet row with the actual `/command` string — to be confirmed against the current Lumina.Excel.Sheets version when implemented, the same "confirm against current API surface" caveat already applied to Moodles/Glamourer/Penumbra IPC in this codebase). Emotes with no resolvable command are excluded from the gesture picker's list, rather than being selectable and failing at fire time.
9. **The gesture reaction sends its resolved command through the existing `ChatMessageSender`**, not a new mechanism — a gesture's command is just another string sent through the same chatbox-submission path already used for the chat-message reaction. It shares that reaction's per-trigger cooldown and last-sent tracking rather than getting its own, since both exist to protect against the same chat-spam throttle; a trigger firing both in the same tick only needs one guard.
10. **Gesture reactions are not tracked in `ActiveEffectRegistry`** — like the chat-message reaction, they fire once and are done. There's no "revert a gesture" concept.

### Config UI
11. **The existing `ConfigWindow` is reorganized in place**, not replaced by a new window: a top-level tab bar with "Active Effects", "Triggers", and "Settings" tabs. "Active Effects" holds what `MainWindow` used to show (the live active-effects list and "Force revert all"), minus its "Show Settings" button, which is no longer needed once everything is one window; "Triggers" holds the master-detail layout (filterable list + detail pane); "Settings" holds the two settings checkboxes that used to float above the trigger list. `MainWindow` is deleted and `Plugin.cs`'s `ToggleMainUi`/`ToggleConfigUi` both now target the single `ConfigWindow` instance. (This reverses an earlier version of this decision, which kept the two windows separate on the reasoning that a glanceable status view and a configuration screen serve different moments; explicit user direction during implementation asked for one window instead.)
12. **Detail-pane sections (Source / Reactions / Timing & Revert) are plain grouped blocks with header text and a separator**, not nested collapsing headers — keeps the whole trigger visible at once (matching the reference Moodles screenshot's layout) rather than requiring further expand/collapse interaction on top of the outer list selection.
13. **The list label falls back through: configured `Name` -> a per-source-type generated label** (emote name / chat phrase in quotes / action name) — computed the same way the existing header label is today (`emotes.TryGetValue(...)`), just extended with the two new source types and gated by whether `Name` is set.

### Bug fix: Penumbra stage application
14. **`PenumbraIpc` uses Penumbra's temporary-settings IPC, not its permanent mod-settings IPC.** Revised after user feedback: the original implementation drove `TrySetMod`/`TrySetModSetting` (Penumbra's *permanent* API — a real, persisted write to the mod's own configuration file), which is wrong for an automation overlay: a crash, unexpected shutdown, or simply disabling ReactToMe could leave a mod stuck enabled in the user's real settings. Penumbra publishes a parallel temporary-settings family scoped per player object (`SetTemporaryModSettingsPlayer`/`RemoveTemporaryModSettingsPlayer`, confirmed against Ottermandias/Penumbra.Api's `IpcSubscribers/Temporary.cs`) built exactly for this — it takes the local player's object index directly, and clearing it restores the mod to whatever its permanent configuration already was, not a hard-coded disabled state. `SetTemporaryModSettingsPlayer`'s `inherit` parameter maps to Penumbra's internal `ForceInherit` flag — passing `true` would make our own `enabled`/`settings` values inert (falls through to the permanent config instead), the opposite of what's needed, so it's `false`. A fixed key (`TemporarySettingKey`) is passed to every set/remove call so only ReactToMe's own calls can manage the temporary settings it creates.
15. **`PenumbraIpc`'s enable-and-set-option call checks the returned `PenumbraApiEc` from both the set and remove temporary-setting calls**, logging and showing the existing IPC-failure chat warning for any result other than `Success`/`NothingChanged` — the original implementation discarded both results entirely, so a rejection (for example `InvalidCredentials`, if Penumbra's IPC permission gate hasn't finished granting access when the very next call fires) was completely silent. This makes the failure visible; it does not add retry or delay logic, since the exact root cause hasn't been confirmed by a live repro with the new logging in place yet.
16. **`SetStage` reads the mod's current effective priority before setting a temporary override, rather than hard-coding a priority.** `SetTemporaryModSettingsPlayer` requires a `priority` argument on every call, and an initial implementation passed a fixed `0` — which silently overwrote a priority the user had deliberately configured (e.g. `4`) for the duration of the override. `GetCollectionForObject` is brought back (dropped in Decision 14, needed again here) purely for this read: resolve the local player's collection, then call the permanent-side `GetCurrentModSettings(collectionId, modDirectory, modName, ignoreInheritance: false)` — a read-only call, not a permanent write — and pass its returned priority straight through. Falls back to `0` only if that read fails or the mod has no resolvable settings at all.

## Risks / Trade-offs

- [Risk] `ChatMessage` events fire extremely frequently in busy areas (Limsa market wards, alliance raids) — case-insensitive substring matching against every trigger's phrase on every message could add up → Mitigation: short-circuit on `IsEnabled`/`HasAnyAction` before string matching, same as `TriggerMatcher` already does for emotes; revisit with per-trigger compiled matchers only if this proves measurably costly.
- [Risk] `CastInfo` layout is sourced from a community-maintained reverse-engineering project (FFXIVClientStructs) and can shift across game patches → Mitigation: same risk class already accepted for `EmoteController.EmoteId` via the same project; no new risk category introduced.
- [Risk] The Penumbra bug fix's root cause is a documented hypothesis (an IPC permission-grant race), not a confirmed diagnosis → Mitigation: the fix (surfacing `PenumbraApiEc` failures) is valuable regardless of whether that specific hypothesis is correct, since it turns a silent failure into a visible, diagnosable one either way.
- [Risk] Reworking `ConfigWindow` this substantially risks losing existing behavior (search filters per picker, the `Refresh lists` button, disabled-state UI) in the shuffle → Mitigation: tasks.md should treat every existing control as a checklist item to relocate, not just describe the new layout in the abstract.
- [Risk] `SetTemporaryModSettingsPlayer`'s `settings` dictionary only ever contains the one option group ReactToMe is setting — whether Penumbra leaves the mod's *other* option groups inherited from the permanent config, or resets them to a default, isn't confirmed from source alone and needs a live check. If it resets them, a mod with multiple independent option groups could show unexpected values in its untouched groups while a ReactToMe stage is active → Mitigation: none implemented; flagged for the manual verification pass (a mod with 2+ option groups, only one staged, checked before/during/after firing).
