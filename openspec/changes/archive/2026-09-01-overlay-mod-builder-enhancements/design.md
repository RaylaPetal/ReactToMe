## Context

See proposal.md for motivation. Current state this builds on (`ReactToMe/OverlayModBuilder/`):

- `OverlayModBuilderStage` tracks `OverlayImagePath`, `LastBakedOverlayImagePath`, `LastBakedSnapshotVersion`, `LastBakedFileSchemeVersion`, and `NeedsRebake(currentSnapshotVersion)` compares all three against the project's current state — a stage's own overlay and the project-wide snapshot/scheme versions are the only things staleness ever depends on today.
- `OverlayModBuilderService.BakeStageAsync` always composites a stage's overlay against `project.PristineSnapshotPath` (loaded fresh via `Image.Load<Rgba32>` each time), never against another stage's output — this is the exact behavior proposal.md is replacing with chaining.
- `BakeStageAsync` also saves a preview PNG at `Path.ChangeExtension(stageFilePath, ".png")` next to the baked `.tex`, purely for the UI thumbnail today — this design reuses that same file as the next stage's composite input, so no new decode step is needed.
- `OverlayModWriter.RedirectGamePath` is a fixed constant; the mod always has exactly one single-select group named "Stages" with one option per stage with a baked file.
- `OverlayModWriter.ApplyProject` decides `AddMod` vs `ReloadMod` purely from `project.IsApplied` — there's no way today to force `AddMod` again once a project has applied successfully once, which is exactly the gap "Recreate Mod" fixes.
- `PenumbraIpc.GetCurrentPriority` already demonstrates the collection-resolution pattern this change's priority feature reuses verbatim: `getCollectionForObject.Invoke(LocalPlayerObjectIndex)` → `(objectValid, _, collection)` → `collection.Id`.

## Goals / Non-Goals

**Goals:**
- Each stage after the baseline visibly builds on the previous stage's own baked look, not just on the pristine base.
- The pristine snapshot itself is always available as a selectable, no-overlay option in the generated mod (Stage 0), without the user having to create it manually.
- A project can recover from having its generated mod deleted directly in Penumbra, without losing its stages or having to recreate the project from scratch.
- A project's generated mod can be given a priority that actually takes effect in Penumbra, so it can be made to reliably win (or lose) against a conflicting mod.

**Non-Goals:**
- No UI for reordering stages — the chain is always in the stage list's existing order; reordering is a plausible future extension, not required now.
- No per-stage priority — priority is one value per project (per mod), matching Penumbra's own per-mod (not per-option) priority model.
- No retroactive migration of existing projects' already-baked stages into the new chained scheme automatically beyond what staleness detection already forces — an existing project's stages will simply all be considered stale once this ships (see Risks) and get re-baked in chain order the next time the project is applied or rebaked, same as any other scheme-version bump this session has already done twice.

## Decisions

- **Stage 0 is a real, ordinary `OverlayModBuilderStage`, not a separate concept.** It is auto-inserted at index 0 (empty `OverlayImagePath`, name "Stage 0") the first time a project's snapshot is captured, if not already present. Reusing the exact same stage/staleness/baking machinery for it (rather than a parallel "baseline" code path) means every other decision in this design — chaining, staleness, mod-writing — applies to it automatically. The UI simply refuses to let the user remove or rename index 0's stage. `BakeStageAsync` gets one special case: when `stage.OverlayImagePath` is empty (true only for Stage 0), it skips compositing and copies the pristine snapshot directly into that stage's own baked file and preview — every other stage still requires a non-empty overlay image, unchanged from today.
- **Chaining reuses each stage's own already-saved preview PNG as the next stage's composite base**, instead of re-decoding the previous stage's `.tex` output via Penumbra's `ConvertTextureFile` IPC again. `BakeStageAsync(project, stage)` loads `Image.Load<Rgba32>(previousStage's preview PNG path)` when `stageIndex > 0`, or the pristine snapshot when `stageIndex == 0`. This avoids adding a second decode path and keeps the previous stage's own preview file doing double duty as both "what the UI shows" and "what the next stage bakes from," which are the same pixels by construction.
- **Chain staleness is tracked with a per-stage monotonic `BakeVersion` counter, extending the same version-comparison pattern already used for `SnapshotVersion`/`StageFileSchemeVersion`.** Each stage gains `BakeVersion` (incremented every time that stage successfully bakes) and `LastBakedPredecessorVersion` (the previous stage's `BakeVersion` at the time this stage last baked; for Stage 0, this concept doesn't apply — its own staleness is governed by `SnapshotVersion` alone, unchanged from today). `NeedsRebake` for stage `N > 0` becomes true when its own overlay image changed, the file scheme changed, *or* `LastBakedPredecessorVersion != stages[N-1].BakeVersion`. This means re-baking Stage 1 automatically cascades: Stage 2 sees Stage 1's `BakeVersion` changed and is marked stale, and so on down the chain — `ApplyProjectAsync`'s existing in-order stage loop already bakes stages in ascending index order, so a cascade is always resolved correctly within a single apply pass without needing a separate propagation step.
- **"Recreate Mod" is the existing apply path plus one new flag, not a separate pipeline.** The shared private `ApplyProjectAsync(project, forceRebakeAll)` gains a second flag, `forceAddMod`, which — only when set — calls `AddGeneratedMod` unconditionally instead of branching on `project.IsApplied`. `RecreateModAsync(project)` is a thin public wrapper calling this with both flags true (force a full in-order re-bake, since Penumbra having lost the mod is a good reason to distrust on-disk state too, and force `AddMod`). This mirrors exactly how `RebakeAllAsync` was already layered onto the same shared method earlier this session.
- **Priority is applied via a new `PenumbraIpc.SetModPriority(modDirectory, modName, priority)` wrapper around `TrySetModPriority(collectionId, modDirectory, modName, priority)`**, resolving `collectionId` via the same `getCollectionForObject.Invoke(LocalPlayerObjectIndex)` pattern `GetCurrentPriority` already uses. Called once, after a successful `AddGeneratedMod`/`ReloadGeneratedMod`, from the same place in the service that already knows the apply succeeded — not folded into `OverlayModWriter` itself, since priority is a live Penumbra collection setting, unrelated to anything written into the mod's own files on disk.
- **`OverlayModBuilderProject.Priority` defaults to `0`** (Penumbra's own default for a newly-registered mod), so a project that never touches this field behaves exactly as today — applying is a no-op regarding priority in that case rather than forcing a `SetModPriority` call for every project regardless of whether the user cares.

## Risks / Trade-offs

- [Risk] Every stage of every already-applied project becomes stale the moment this ships, since none of them have a `BakeVersion`/`LastBakedPredecessorVersion` history and Stage 0 doesn't exist for them yet. -> Not mitigated further; this repeats the same, already-accepted pattern from the `StageFileSchemeVersion` bump earlier this session — the next Apply/Rebake All simply re-bakes everything in order, which is correct (if not free) behavior, not data loss.
- [Risk] Chaining means a broken or ugly intermediate stage propagates into every stage after it, unlike today's independent-per-stage compositing where one bad stage can't affect another. -> Not mitigated in this pass; this is the explicitly requested behavior (each stage builds on the previous one), so a bad stage affecting its successors is intentional, not a bug — the existing preview thumbnail per stage lets the user catch a bad intermediate stage before it propagates further.
- [Risk] `TrySetModPriority` is confirmed to exist in Penumbra's own API source with the expected signature, but has not been exercised live against the user's installed Penumbra version the way the mod-file format was spiked earlier this session. -> Mitigation: task 1 verifies this IPC call live (set a priority on the test/spike mod or an existing overlay project, confirm in Penumbra's own UI the value actually changed) before it's wired into the main apply path, following the same "verify before building on it" approach the original hard-gated spike used — proportionate to this being a single, already-declared IPC call rather than an entire unverified file format.
- [Risk, materialized] Found live while testing this change, before archiving: the base-texture picker's "unfiltered" list (a deliberate decision from the prior `overlay-mod-builder` change) showed far more than the user could use in practice — vanilla's own deeply-nested `chara/human/.../obj/<part>/...` paths for every equipped item and body part, plus other mods' absolute file paths, all mixed in with the one or two entries that were ever actually relevant. -> `PenumbraIpc.GetTextureOverlayCandidates` now filters to paths whose immediate parent directory is named `chara` (`IsDirectCharaPath`) — every real target this tool has actually been pointed at (`chara/bibo_mid_base.tex`, `chara/kaede overlay.tex`) fits that exact shape, so this narrows the list without excluding anything that's ever mattered. This revises the prior change's "deliberately unfiltered, no naming-convention filtering" decision, now that live use showed the earlier concern (a `_d.tex`-suffix/vanilla-path heuristic missing real body-mod paths) doesn't apply to a structural "what's the immediate parent directory" check the way it applied to a filename-suffix or exact-full-path heuristic.
- [Risk, materialized] The first version of this filter required the path to *start with* `chara/` (forward slash), which excluded exactly the case it was meant to include: an absolute Windows path like `Z:\...\Skin Overlay Kaede\chara\kaede overlay.tex` uses backslashes and an arbitrary prefix before `chara`, so it never starts with `chara/` at all even though `chara` is genuinely its immediate parent directory. -> Fixed by splitting on both `/` and `\` and checking only the second-to-last segment, so an arbitrary prefix (or none, for a clean virtual path) before `chara` no longer matters — only that `chara` directly contains the file.
- [Risk, materialized] Even with that fix, the picker still came back completely empty during testing. A temporary debug dump of Penumbra's raw resource list (added and removed once it had served its purpose) showed the immediate cause: nothing in that particular snapshot of the live resource list had `chara` as its immediate parent. The same dump also disproved the prior change's "self-referencing gamePath, empty actualPath means no separate virtual identity" theory: actualPath was empty for every one of the 74 resources dumped, not just ones without a separate identity — later confirmed against Penumbra's own source to be because the tuple is actually `(fullPath, name, icon)`, not `(gamePath, actualPath, icon)`.
- [Risk, materialized] Reading "whatever Penumbra currently reports as resolving" turned out to be an unreliable sole source for this tool's actual need (know a redirect exists, not whether it's presently winning on-screen) — the user's own target still didn't appear even after the tuple-semantics fix. -> Rather than keep trying to explain *why* the live list was missing an entry, `GetTextureOverlayCandidates` now combines it with a second source: every installed mod's own declared file redirects, read directly from that mod's `meta.json` on disk, independent of render state or whether the mod is even enabled (`AddModDeclaredCharaFiles`). Both sources are filtered by the same "chara"-immediate-parent check and merged into one deduplicated list, so whichever source actually has a given target surfaces it — this trades a small amount of redundant work for not depending on a single source's blind spots.
