## 7. End-to-end verification

- [x] 7.0 Found while testing live, before archiving: the base-texture picker's unfiltered list (from the prior `overlay-mod-builder` change) mixed in vanilla's own deeply-nested `chara/human/.../obj/<part>/...` paths for every equipped item and body part, plus other mods' absolute file paths, alongside the one or two entries actually relevant. Fixed by filtering `PenumbraIpc.GetTextureOverlayCandidates` to game paths sitting directly under `chara/` with no further subdirectory (`IsDirectCharaPath`) — the exact shape every real target this tool has been pointed at (`chara/bibo_mid_base.tex`, `chara/kaede overlay.tex`) actually has. Revises the "Base texture is picked from a searchable, unfiltered live list" requirement from the archived `overlay-mod-builder` change (delta spec updated here as a MODIFIED requirement).
- [x] 7.0a Found immediately after 7.0's filter shipped: the base-texture picker came back completely empty, even for paths that should trivially match. First attempted fix (require the path to *start with* `chara/`) was wrong — it excluded exactly the absolute-path case (`Z:\...\chara\kaede overlay.tex`, backslashes, arbitrary prefix) it was meant to include. Fixed `IsDirectCharaPath` to split on both `/` and `\` and check only the second-to-last segment, so an arbitrary prefix (or none) before "chara" no longer matters. A temporary debug dump of Penumbra's raw resource list (added and then removed once its purpose was served) then showed the *actual* remaining cause: at the moment of testing, none of the 74 currently-active `.tex` resources had "chara" as their immediate parent at all — the Kaede overlay resource (and the plain `chara/bibo_mid_base.tex` path) simply weren't in Penumbra's live resource list right then, most likely because the character's current worn gear wasn't exposing the body skin the redirect targets. Not a code bug: Penumbra only reports resources it's actually currently rendering. The same dump also disproved this session's earlier "self-referencing gamePath/empty actualPath" theory (from the prior `overlay-mod-builder` change) — actualPath was empty for literally every one of the 74 resources, not just ones with no separate virtual identity, so the doc comments explaining that fallback were corrected to say so plainly rather than repeat the disproven theory.
- [x] 7.0b Found while chasing 7.0a's empty-dropdown report further: even after confirming the "chara"-parent filter logic was correct (verified with a narrower diagnostic dump), the expected resource still never appeared. Fetched Penumbra's own source (`ResourceTreeApiHelper.GetResourcesOfType`) directly and confirmed `GetPlayerResourcesOfType`'s per-resource tuple is `(fullPath, name, icon)`, not `(gamePath, actualPath, icon)` as this tool had assumed since the original `overlay-mod-builder` change — there is only one real path per resource; "name"/"icon" need `withUiData: true` to populate and are irrelevant here. This didn't explain the empty list either. Switched `GetTextureOverlayCandidates` to instead scan every installed mod's own `meta.json` directly off disk (`DefaultData.Files` plus every group/option's `Files`), independent of render state or whether a mod is enabled, filtered the same way (immediate parent directory named "chara").
- [x] 7.0c The mod-scan alone still didn't surface the user's target (their overlay mod likely uses a shape the scan doesn't handle, e.g. separate `group_NNN.json` files — see the caveat left in `AddModDeclaredCharaFiles`'s doc comment). Per the user's direct instruction, reverted to combining *both* sources rather than picking one: the original live-resolution approach (confirmed to have worked before any filtering existed) plus the mod-file-scan, merged into one deduplicated candidate dictionary, both filtered by the same "chara"-immediate-parent check. Whichever source actually has a given target now surfaces it.
- [x] 7.0d Found once the picker itself worked and the user could actually test the chained-baking/apply pipeline end to end: the per-stage preview thumbnail intermittently showed "(preview file exists but failed to load as an image)". Root cause: `Plugin.TextureProvider.GetFromFile(path).GetWrapOrDefault()` is a file-path-keyed cache Dalamud maintains for static plugin assets — it isn't designed for a file that gets overwritten in place on every rebake (this preview PNG does exactly that), so it can get stuck on a stale or failed load from before the file existed. Fixed by decoding the preview ourselves via ImageSharp and uploading it with `ITextureProvider.CreateFromRaw`, cached in `ConfigWindow` keyed by path + the file's own last-write time so a rebake is correctly picked up, disposed in `ConfigWindow.Dispose()`.
- [x] 7.0e Per direct user request: removed the routine step-by-step `chatGui.Print` diagnostics added earlier while chasing the apply-pipeline silent-failure bug (capturing/baking/applying progress lines, per-stage `needsRebake=` lines) — `chatGui.PrintError` calls for actual failures are kept, since there's no other surfaced error UI. Replaced the removed progress feedback with disabling each project's action buttons (Capture/Recapture, per-stage Browse/Remove, Apply, Rebake All, Recreate Mod) for the duration of that project's in-flight operation, plus a "Working..." label, via a new `RunOverlayBusyTask` helper and a `busyOverlayProjectIds` set — the UI's own state (snapshot/stage/"Applied to Penumbra" text, previews) already reflects the result once an operation finishes, so a chat line was never actually needed for the success path.
- [x] 7.0f Per direct user request: clicking a stage's preview thumbnail now opens an enlarged view in a popup, reusing the same cached-raw-texture loader from 7.0d (`TryGetOverlayPreviewWrap`) rather than decoding twice. The popup is opened from `DrawOverlayModBuilderTab`'s own top-level scope (not from inside the stage loop's `PushID`) so its identity is never mangled by whichever stage's thumbnail was actually clicked.
