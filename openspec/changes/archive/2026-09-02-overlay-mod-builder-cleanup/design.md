## Context

See proposal.md for motivation. Current state this builds on (`ReactToMe/OverlayModBuilder/`, `ReactToMe/Ipc/PenumbraIpc.cs`):

- `OverlayModWriter.GetStageRelativeFilePath(int stageIndex) => $"chara/reacttome_overlay_stage{stageIndex}.tex"` — a stage's on-disk file identity is purely its current position in `project.Stages`. `OverlayModBuilderService.BakeStageAsync` and `OverlayModWriter.ApplyProject` both derive a stage's file path this same way, keyed by `project.Stages.IndexOf(stage)` / a loop index.
- Removing a stage today is just `project.Stages.RemoveAt(removeIndex)` in `ConfigWindow.cs` — no file cleanup, and every stage after the removed one silently inherits a new index (and therefore a different on-disk file) the next time it bakes, while whatever file used to belong to that index is left on disk untouched until something overwrites it.
- `OverlayModWriter.StageFileSchemeVersion` (currently `2`) already exists specifically to force a re-bake past a code-level path-scheme change, compared against each stage's own `LastBakedFileSchemeVersion` in `OverlayModBuilderStage.NeedsRebake`.
- "Remove Project" in `ConfigWindow.cs` only calls `configuration.OverlayModBuilderProjects.Remove(project)` — it never calls anything in Penumbra, by original design (its own tooltip says so).
- `PenumbraIpc` already has the collection/mod-management pattern this change reuses: `AddGeneratedMod`/`ReloadGeneratedMod` wrap `AddMod`/`ReloadMod` with the same `IsAcceptable(PenumbraApiEc)` check this change's new `DeleteMod`/`SetModPath` wrappers will follow. Penumbra's own IPC subscriber `Invoke` signatures (confirmed from source, not just the interface): `DeleteMod.Invoke(modDirectory, modName = "")` and `SetModPath.Invoke(modDirectory, newPath, modName = "")` — both reorder/default relative to the `IPenumbraApiMods` interface's own declared parameter order, the same gotcha `TrySetModPriority` had earlier this session.
- `ReactionTrigger.PenumbraStages` is a `List<PenumbraStageThreshold>`, each with `Threshold` (int, fire-count at which it activates), `ModDirectory`, `ModName`, `OptionGroupName`, `OptionName` — a fully self-contained mod/group/option target per threshold, matching exactly what `OverlayModWriter.ApplyProject` already writes (mod directory `OverlayModWriter.GetModDirectoryName(project.Id)`, group always named `"Stages"`, option name = each stage's `Name`). `ReactionTrigger.PenumbraReactionMode` must be `Staged` for this list to take effect (see `GetEffectivePenumbraMode`'s backward-compatible resolution).

## Goals / Non-Goals

**Goals:**
- A stage's on-disk files are never affected by adding/removing any other stage in the same project.
- Removing a stage actually frees the files it used, instead of leaving them until something else happens to overwrite them.
- Removing a project cleans up the real Penumbra mod it produced, not just ReactToMe's own record of it — but never without the user explicitly confirming.
- A project can be filed into a Penumbra mod-list folder the same way doing it by hand in Penumbra's UI would.
- A project can generate a trigger with its stages already wired up as `PenumbraStageThreshold` entries, so the user only has to configure what fires it.

**Non-Goals:**
- No bulk "clean up all orphaned ReactToMeOverlay-* mods" scan — this only ever acts on a specific project the user is actively removing.
- No UI for browsing Penumbra's existing folder structure to pick from — the folder field is a plain path the user types, matching how Penumbra's own path field works today.
- No change to how a project's mod is identified or looked up (`OverlayModWriter.GetModDirectoryName`) — only which relative path a *stage's own file* has, and where the *whole mod* sits in Penumbra's sort order.

## Decisions

- **Each `OverlayModBuilderStage` gets a permanent `Id` (Guid, assigned on construction), and `GetStageRelativeFilePath` keys off that `Id` instead of the stage's list index.** This is the direct fix for the reported bug: a stage's file identity no longer depends on where it sits in the list, so removing one stage can never cause another stage to start reading or writing a different file than it already was. New signature: `GetStageRelativeFilePath(Guid stageId) => $"chara/reacttome_overlay_stage_{stageId:N}.tex"`. Every caller that today passes a loop/list index (`OverlayModBuilderService.BakeStageAsync`, `GetStagePreviewPath`, `OverlayModWriter.ApplyProject`) passes the stage's own `Id` instead. Chain order (which stage is "the previous one" for compositing) still comes from list position (`project.Stages.IndexOf(stage)` / a loop index) — only *file naming* moves off position, chaining semantics don't change.
- **This is another `StageFileSchemeVersion` bump** (the established pattern from the prior two changes), so every existing project's stages are correctly forced to re-bake once under the new Id-based scheme rather than silently pointing at their old index-named files forever.
- **Stage removal deletes its own baked `.tex` and preview `.png` immediately**, via a new `OverlayModBuilderService.DeleteStageFilesAsync`-style helper (synchronous file deletes are fine here — no Penumbra IPC involved) called from `ConfigWindow`'s existing "Remove" button handler, before `project.Stages.RemoveAt(...)`. A missing file (already gone, or never baked) is a no-op, not an error.
- **Project removal deletes the Penumbra mod via a new `PenumbraIpc.DeleteMod(modDirectory, modName)` wrapper**, called only when `project.IsApplied` (never applied = nothing to delete), and only after the confirmation step below. Penumbra's own `DeleteMod` handles removing the mod's files/folder itself — this change does not separately delete the mod folder from disk.
- **Confirmation is a two-click pattern already idiomatic for this codebase's destructive actions**: "Remove Project" becomes a two-stage button — first click turns it into a "Confirm Remove (deletes Penumbra mod too)" state (only when `project.IsApplied`; an unapplied project still removes on the first click, per the spec's "needs no Penumbra cleanup" scenario), second click within the same session actually removes+deletes. Chosen over a popup modal to keep the interaction inline and match this tab's existing lightweight button-driven style, rather than introducing a new UI pattern for one action.
- **The Penumbra folder is applied via a new `PenumbraIpc.SetModPath(modDirectory, newPath, modName)` wrapper**, called from the same place in `OverlayModBuilderService`'s apply path that already calls `SetModPriority` after a successful `AddGeneratedMod`/`ReloadGeneratedMod` — same "only act if the project actually configured something" pattern already used for priority (`project.Priority != 0`), here `project.PenumbraFolder.Length > 0`. `newPath` is constructed as `$"{project.PenumbraFolder}/{project.DisplayName}"` (Penumbra's own sort-order path convention includes the mod's own display segment at the end, the same way a user typing a path in Penumbra's UI would).
- **"Create Trigger" builds a `ReactionTrigger` directly from a project's current baked stages, threshold = 1-based ascending position among baked stages** (first baked stage → 1, second → 2, ...) — matches "higher fire count escalates further" and mirrors the order stages already appear in the project; an unbaked stage (no file at its expected path) is skipped, exactly like `OverlayModWriter.ApplyProject` already skips one when writing the mod's own options. Sets `PenumbraReactionMode = Staged` explicitly (never left at the default `None`, since a resolver that treats "already-populated `PenumbraStages`" as `Staged` for backward compatibility is not a reason for new code to skip setting it correctly). The new trigger is added to `configuration.Triggers` and the UI switches to the Triggers tab with it selected — the fastest path to the one thing left to configure (its fire source) — rather than leaving the user to go find it themselves in a potentially long trigger list.

## Risks / Trade-offs

- [Risk] Bumping `StageFileSchemeVersion` again forces every existing project's stages to re-bake on their next Apply/Rebake All, same as the last two times this scheme changed. -> Not mitigated further; same already-accepted trade-off as before — correct behavior, not data loss, and the "Rebake All" escape hatch already exists for forcing it explicitly.
- [Risk] The two-click "confirm remove" pattern could be accidentally completed by a fast double-click. -> Not mitigated with a timeout or separate modal in this pass, since the target audience is a single user working through their own projects deliberately; revisit only if this proves to be a real problem in practice.
- [Risk] `SetModPath`'s exact expected format for `newPath` (whether it must include the mod's own display-name segment, or just the folder) is inferred from Penumbra's own doc comment ("internal search order and filesystem path... including search order") rather than verified live. -> Mitigation: task 1 verifies this live (apply a project with a folder set, confirm in Penumbra's own UI it's actually filed under that folder with the expected display name) before considering the feature done, consistent with this session's established "verify a new IPC call live before trusting it" practice.
