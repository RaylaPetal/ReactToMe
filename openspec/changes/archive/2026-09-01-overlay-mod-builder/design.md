## Context

See proposal.md for motivation — this replaces the reverted `penumbra-texture-overlay` change's live-redirect approach with the "bake a real mod, let the existing staged-mod reaction apply it" approach `Sebane1/DragAndDropTexturing` actually uses.

Three pieces of that reverted attempt are being re-established here unchanged, because they were proven correct before things went wrong elsewhere: the searchable, unfiltered live-texture picker (`GetPlayerResourcesOfType` -> flat game-path list, no naming-convention filtering); decoding a base `.tex` via Penumbra's own `ConvertTextureFile` IPC rather than Lumina's own BC decompression (which produced visibly scrambled output for at least one real body mod); and ImageSharp-based compositing with the output forced fully opaque (a real body-texture's own "alpha" channel isn't necessarily real transparency).

What's new here is producing a real, permanent Penumbra mod file structure. `Sebane1/LooseTextureCompilerCore` (the texture-compilation core behind DragAndDropTexturing) was fetched and read directly for this — its `Json/ModMeta.cs`, `Json/Group.cs`, and `Json/Option.cs` give a concrete, working reference:

```csharp
// meta.json (top level)
{ FileVersion, Name, Author, Description, Version, Website, ModTags,
  DefaultData: { Files, FileSwaps, Manipulations },
  Groups: [ Group, ... ] }   // groups embedded inline, not separate files, in this reference

// each Group
{ Name, Description, Priority, Type: "Single" | "Multi", DefaultSettings,
  Options: [ Option, ... ] }

// each Option
{ Name, Priority, Files: { "<game path>": "<mod-relative file path>" }, FileSwaps, Manipulations }
```

This is one real, working schema shape — but it may not exactly match what the currently-installed Penumbra version expects (schema versions drift, and Penumbra's own UI has historically also supported separate `group_NNN_<name>.json` files rather than groups embedded in `meta.json`). This is exactly the "materialized risk" category from the reverted attempt — a document assumption that looked reasonable but needed live verification twice before things actually worked. It is not being treated as settled; see the spike in tasks.md.

## Goals / Non-Goals

**Goals:**
- Produce a real Penumbra mod that Penumbra's own UI shows and manages normally — no synthetic runtime redirect, no new fire-time IPC surface.
- Keep the trigger-firing system (the staged-Penumbra-mod reaction) completely untouched — this change only ever produces mods for it to point at, the same as if the user had built them by hand.
- Re-applying a project updates one stable mod in place rather than accumulating duplicates.
- Every stage bakes independently from one pristine, deliberately-captured snapshot — never cumulatively, never against a possibly-already-altered live texture.

**Non-Goals:**
- No multi-target projects in this pass (one project = one target game path = one option group). A project bundling multiple targets as multiple groups in one mod is a plausible future extension, not required now.
- No UV/resolution validation of imported overlays — same limitation as the reverted attempt; overlays must already match the target's layout.
- No automatic re-bake when the live texture changes — recapturing the pristine snapshot is a deliberate, explicit action.
- No support for normal/mask/specular targets, and no arbitrary redirect target at all *(revised after implementation — see Risks)*: a project reads pixel data from whatever live texture the user picks (any `.tex` resource, "let the user recognize their own path"), but the generated mod's redirect target is always the fixed Bibo body base path (`OverlayModWriter.RedirectGamePath`) — this tool exists specifically for staged Bibo-body overlays, not general-purpose texture redirection.

## Decisions

- **Reuse the proven pieces from the reverted attempt verbatim**: the unfiltered searchable texture picker, `ConvertTextureFile`-based decode, and forced-fully-opaque ImageSharp compositing. These were never the source of any bug found during that attempt — only the live-application half was. Re-deriving them from scratch would be wasted risk.
- **Mod file authoring based on `LooseTextureCompilerCore`'s schema, verified by spike before building on it.** Rather than trust the reference schema directly, task 1 hand-authors the smallest possible mod (one group, one option, one dummy texture) and requires the user's live confirmation in Penumbra's own UI before any further work proceeds. If the embedded-groups shape doesn't hold, the fallback is separate `group_001_<name>.json` files (Penumbra's other well-documented convention) — a same-sized change to the writer, not a redesign.
- **Single-select group type**: the generated group's `Type` is always `"Single"`, so Penumbra itself enforces "only one stage active" — a correctness guarantee beyond whatever the trigger's own logic already does, not a replacement for it.
- **Pristine snapshot stored in ReactToMe's own plugin data directory** (not inside the generated mod), captured once per project and reused for every stage's bake. Recapturing is a separate, explicit action (mirroring "Rebake" from the reverted attempt, but for the base rather than a single stage).
- **Stable per-project mod identity for update-in-place re-applying**: each project gets a fixed, generated mod directory name (derived from the project's own id, not its display name, so renaming a project doesn't orphan its mod). Re-applying overwrites that same directory's files and calls `ReloadMod`; it never calls `AddMod` a second time for the same project once already registered.
- **Stages carry no fire-count/threshold data at all.** That concept belongs entirely to the trigger side's existing `PenumbraStageThreshold` list, which already lets a trigger map "fire count N -> mod/group/option" against any mod. This builder only ever needs to produce named options; how a trigger later escalates through them is unrelated, pre-existing, unmodified configuration.
- **Stage files use a fixed on-disk path, decoupled from the target game path's own content** *(revised twice after implementation — see Risks)*. `OverlayModWriter.GetStageRelativeFilePath` always returns `chara/reacttome_overlay_stage{N}.tex`, regardless of the project's target — this satisfies the one thing actually confirmed live (the top-level folder must be named `chara`, directly under the mod root; the file name never mattered), without ever parsing the target string itself. A target picked from the unfiltered candidate list is not guaranteed to be a real virtual game path — it can be a raw absolute override path from another mod — so deriving our own file layout from it is unsafe; see Risks.
- **A bumped `OverlayModWriter.StageFileSchemeVersion` constant, tracked per-stage as `LastBakedFileSchemeVersion`, feeds into `NeedsRebake`.** A code-level change to the on-disk path scheme can never be reflected by a stage's own overlay image or the project's snapshot version, so without this, every future scheme change would again silently strand already-"successfully baked" stages pointing at a location nothing bakes to anymore (this happened twice before this was added).

## Risks / Trade-offs

- [Risk] The mod-file schema (embedded groups in `meta.json` vs. separate `group_NNN.json` files, exact required fields, `FileVersion` value) may not match what the currently-installed Penumbra version actually expects — this is new, unverified territory, unlike anything already proven this session. -> Mitigation: task 1 is a hard-gated spike requiring the user's live confirmation in Penumbra's own UI before any further implementation proceeds, exactly because this session already saw multiple cases where something that compiled and "looked right" from static analysis alone was wrong in ways only live testing caught.
- [Risk] Writing directly into Penumbra's mod directory is a genuinely permanent, visible change to the user's Penumbra setup (unlike everything else this plugin does, which is temporary/reversible) — a bug here could leave a broken or duplicate mod behind. -> Mitigation: stable per-project identity keeps re-applies idempotent (update, not duplicate); the user can always delete a generated mod from Penumbra's own UI like any other mod, since it's a completely normal mod once created.
- [Risk] If Penumbra's own mod-file watcher or `AddMod`/`ReloadMod` IPC doesn't pick up changes the way expected, the user could see a stale mod until a manual Penumbra-side rescan. -> Not fully mitigated in advance; the spike should specifically confirm `ReloadMod` reflects an edited option's file correctly, not just that `AddMod` registers the mod initially.
- [Risk] Two projects could target the same game path with two separately-generated mods, both enabled — Penumbra's own priority resolution decides which wins, same as any two real mods conflicting. -> Not mitigated further; this is normal, expected Penumbra behavior for conflicting mods, not a new problem this feature introduces.
- [Risk, materialized] The first live end-to-end test placed a stage's baked file flat at the mod's root, and the mod did not apply correctly. -> Resolved by mirroring the target game path's own directory structure inside the mod folder instead, with a per-stage-unique file name (see Decisions above) — a real working mod's own layout was checked directly, and confirmed the file's exact name doesn't matter, only that the mirrored top-level folder (e.g. "chara") sits directly under the mod root, not nested under any other folder.
- [Risk, materialized] Separately, applying the directory-mirroring fix above produced a mod with zero options — not a path-shape problem this time, but a staleness-tracking gap: a stage already marked "successfully baked" (under the old, wrong scheme) never got re-baked at the new path, since neither its overlay image nor the snapshot version had changed. -> Resolved by adding `OverlayModBuilderService.RebakeAllAsync` (force-bakes regardless of staleness) as a general escape hatch, plus a diagnostic log naming exactly which expected file was missing for any left-out stage.
- [Risk, materialized] The directory-mirroring scheme itself broke for a target whose "game path" (from the unfiltered candidate list) was actually a raw absolute Windows path rather than a virtual game path — some mods redirect via "whatever's currently resolving" using an absolute path as the Penumbra game-path key. Mirroring split on `/`, found none (the path used backslashes), and returned the entire absolute path as the stage's "relative" path; `Path.Combine` then discarded the mod folder per its own rooted-path rule, silently writing the baked file into the *other* mod's own folder while the new mod's folder stayed empty except for `meta.json`. -> Resolved by making the stage's on-disk path a fixed `chara/reacttome_overlay_stage{N}.tex`, entirely independent of the target's own content, plus a scheme-version bump (see Decisions) so the resulting staleness gap didn't need another manual "Rebake All" to recover from.
- [Risk, materialized] Fixing the on-disk path scheme (above) still left the mod's actual redirect broken, because the `Files` mapping's *key* was also taken directly from the picked candidate's own reported "game path" — for a candidate whose own mod rewrites a material to reference its own file directly (rather than doing a normal virtual-path redirect), that key is that mod's own absolute path, not a real game path Penumbra can honor a redirect against. There was never a way to discover the "real" virtual path from live resource resolution once another mod already claims that slot this way. -> Resolved by dropping the notion of a per-project redirect target entirely: `OverlayModWriter.RedirectGamePath` is now a hardcoded constant (this tool builds Bibo-body overlays specifically, not general-purpose ones — see the revised Non-Goal above), and a project only ever picks which live texture to read pixels *from* (`TargetActualPath`); the picked candidate's own reported path (`SourceGamePath`) is kept purely so the picker reselects the same entry, never used as a redirect key.
