## 7. End-to-end verification

- [x] 7.0 Found during first live end-to-end test: a stage's baked texture was written flat at the mod's root (e.g. `stage0.tex`), and the resulting mod did not apply correctly in Penumbra. Real Penumbra mods mirror the target game path's own directory structure inside the mod folder (e.g. `chara/human/c1801/obj/body/b0001/texture/...`, or just `chara/` for a target like `chara/bibo_mid_base.tex`), and placing a redirect's file at the root instead did not work. Fixed by deriving each stage's file path from the target game path's own directory, with a per-stage-unique file name appended (`OverlayModWriter.GetStageRelativeFilePath`) — e.g. `chara/bibo_mid_base_reacttome_stage0.tex` — used consistently by both the baking step (`OverlayModBuilderService`) and the mod writer's `Files` mapping, so they always agree on where the file lives.
- [x] 7.0a Found re-testing 7.0's fix: the mod applied with zero options (empty). Root cause: changing *where* bakes are written (7.0) didn't invalidate stages that were already marked "successfully baked" under the old flat-file scheme — `NeedsRebake` only tracks the overlay image and snapshot version, neither of which changed, so `ApplyProjectAsync` skipped baking entirely and `OverlayModWriter.ApplyProject` found nothing at the new expected path for any stage, producing zero options. This was a one-time consequence of a code-level path-scheme change, not a recurring user-facing bug, but the underlying gap (no way to force a stage past its own staleness tracking) is a real, permanent one. Added `OverlayModBuilderService.RebakeAllAsync` (force-bakes every stage regardless of `NeedsRebake`) and a "Rebake All" button next to Apply as a general escape hatch, plus a diagnostic log line in `OverlayModWriter.ApplyProject` naming exactly which expected file path was missing for a left-out stage, so a future occurrence of "empty mod" is diagnosable from `/xllog` rather than requiring another guess.
- [x] 7.0b Found while still chasing 7.0a's report: briefly tried a per-stage-subfolder scheme (`stage0/chara/...`) after misreading the report as a path-shape problem, based on comparing against a real working mod's structure. The user corrected this directly: the file's exact name doesn't matter, but `chara` must be the top-level folder directly under the mod root, not nested under any other folder — confirming 7.0's original directory-mirroring-with-suffixed-filename scheme (`chara/bibo_mid_base_reacttome_stage0.tex`) was already structurally correct, and the actual remaining problem was 7.0a's staleness bug. Reverted `GetStageRelativeFilePath` to that original scheme.
- [x] 7.0c Found while diagnosing a persistent "mod applies but nothing is created" report after adding full step-by-step chat diagnostics (per the user's "stop skipping steps" feedback) to every pipeline method: the printed "writing to" path was the *other* mod's own folder (`...\Skin Overlay Kaede\chara\kaede overlay_reacttome_stage0.tex`), not the new `ReactToMeOverlay-<id>` mod folder at all. Root cause: `project.TargetGamePath` for this target was not a normal virtual game path but a raw absolute Windows path (some mods redirect via "whatever's currently resolving," using an absolute path as the Penumbra "game path" key itself). `GetStageRelativeFilePath` mirrored the target's own directory by splitting on `/`, found none (the path uses backslashes), and returned the whole absolute path back as the "relative" path; `Path.Combine(modFolder, thatAbsolutePath)` then discarded `modFolder` entirely per .NET's own rooted-path semantics, silently writing into the unrelated target mod's folder. Fixed by decoupling the stage's on-disk path entirely from the target game path's content: `GetStageRelativeFilePath` now always returns a fixed `chara/reacttome_overlay_stage{N}.tex`, satisfying the one constraint 7.0/7.0b actually confirmed (top-level folder must be named `chara`) without ever parsing the target string. Also added `OverlayModWriter.StageFileSchemeVersion` (a bumped constant) and `OverlayModBuilderStage.LastBakedFileSchemeVersion`, so `NeedsRebake` now automatically detects a code-level path-scheme change and forces a re-bake — this is the second time changing the on-disk scheme silently stranded already-"successfully baked" stages (see 7.0a), so it's now handled structurally instead of via the "Rebake All" escape hatch every time.
- [x] 7.0d Found immediately after 7.0c's fix, live: the generated mod's file redirection still didn't work in Penumbra — the redirect key being written was whatever the picked candidate's own reported "game path" happened to be, which for a mod like the user's own "Skin Overlay Kaede" (an existing personal overlay that already redirects the real body texture, itself rewriting a material to reference its own file directly) is a raw absolute path with no relation to the real virtual path Penumbra needs redirected. There is no per-target virtual game path to discover here at all — the user clarified this tool is scoped to exactly one thing: pick any live-resolving texture as the *source* to read pixels from, and the generated mod always redirects the fixed Bibo body path, with no exceptions and no per-project override. Reworked accordingly: `OverlayModWriter.RedirectGamePath` is now a hardcoded constant (`"chara/bibo_mid_base.tex"`) used unconditionally as the `Files` mapping key; `OverlayModBuilderProject.TargetGamePath` (previously conflated "what to redirect" with "what was picked") was removed and replaced by `SourceGamePath` (cosmetic only, purely for the picker to re-select the same live entry when reopening a project) plus the already-existing `TargetActualPath` (the only thing functionally needed: which live file to read pixels from). The "Redirect game path" free-text override field added in 7.0c's fix was removed entirely as unneeded complexity now that the redirect is fixed.
- [x] 7.0e Found immediately after 7.0d, live: picking the Kaede overlay candidate from the target picker made the rest of the project's UI (capture/stages/apply) disappear entirely instead of opening up. Root cause: `PenumbraIpc.GetTextureOverlayCandidates()` reported this resource with an *empty* actual path — for a resource whose game path already is the terminal resolved file (no separate redirect layer to report), Penumbra's own actual-path field comes back blank rather than repeating the game path — so `TargetActualPath` ended up empty and every UI section gated on it (`if (project.TargetActualPath.Length == 0) return;`) stayed hidden. The tell was visible in the picker itself: a candidate with a real actual path displays as `"<path> (<filename>)"`, and this one displayed as the bare path only. Fixed in `GetTextureOverlayCandidates` itself: when the reported actual path is empty, use the game path as the actual path, since that's already the real file to read from.

Confirmed working live by the user after the 7.0-7.0e bug-fix sequence.
